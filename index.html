Goal engineering gives an AI agent a goal it can check and the limits it works within.

An agent stays goal oriented when it knows what done looks like, which other goals pull against this one and what each is worth, which limits it must hold, how much effort it may spend, and how the goal breaks into smaller ones. This site sets out those parts and carries one example through all of them.

The example

One goal, drawn as a tree

A company asks an agent to cut its monthly cloud bill by a fifth without slowing the checkout page. The bill runs at $84,000 a month, so the agent is done when the billing forecast for the month reads $67,200 or less.

The parts

Six parts make a goal an agent can work toward

Goal

A goal names a state the agent can check for itself, so it knows when it is done and can stop.

In the example The billing forecast for the month reads $67,200 or less.

Counter goal and tradeoff

A counter goal is something else you care about that this goal pulls against, and the tradeoff says which one wins and by how much.

In the example Keep 30% spare compute for the holiday peak. Headroom is worth up to $2,000 a month of savings, and past that the savings win.

Constraint

A constraint is a limit the agent holds whatever the gain, and breaking one counts as failure even when the goal is met.

In the example Checkout p95 stays under 800 ms, nothing is deleted without a person's approval, and only the accounts marked for cost work are touched.

Effort budget

Every goal carries one constraint on effort, which sets how much time, tokens, compute, money and calls to people the agent may spend before it stops and reports.

In the example 2 hours, 400,000 tokens, $15 of compute, and one approval call to a person.

Sub-goals

A goal can split into smaller goals, each checkable on its own, so the goals form a tree the agent works branch by branch.

In the example Three branches with targets that add up to $17,000 a month, against the $16,800 the parent needs.

Milestone

A milestone is a stepping stone the agent reaches on the way to a goal, and since it has no value of its own the agent should reach it well enough to move on and no further.

In the example Tagging buckets matters only because it shows which ones to archive, so the agent does not perfect the tags.

Design time

Design time and runtime

Build in what every job shares, and hand over what each job changes

Some goals are fixed when the agent is built. Others arrive with each job, so the same agent can take a new target, a new budget and a new priority without being rebuilt.

Design time

Built into the agent

  • Its purpose, which every job serves.
  • The hard limits it holds on every job.
  • What it must never trade away, whatever a job asks.
  • What it does when a budget runs out.

Runtime

Handed over with each job

  • This job's goal and the check for done.
  • This job's effort budget.
  • Today's priorities among the counter goals.
  • The sub-goals and milestones, when the person asking already knows them.

If some future job could rightly change a line, hand it over at runtime. If no job should ever change it, build it in. A runtime goal always passes through the design-time limits, so a job can ask for a bigger saving and no job can ask the agent to slow checkout.

Stopping and asking

Say when the agent stops, and when it asks a person

A goal oriented agent also needs to know when to stop working toward the goal. The spec settles four cases before the work starts, so the agent never has to guess at them in the middle of a job.

The goal is met

The agent stops as soon as the check for done passes, even with budget left, and does not spend the rest chasing more.

The budget runs out

The agent keeps what is finished and reports what is left, along with what it would cost to finish.

The goal is out of reach

If the limits put the goal out of reach, the agent says so in its first report instead of spending the budget trying, as it would here if headroom cost the full $2,000 and left the branches at $15,000 against the $16,800 needed.

A person must decide

The agent asks before any step a constraint reserves for a person, and whenever two goals collide in a way the spec does not price.

Where it is heading

One agent today, groups of agents next

Today the bulk of goal engineering is about a single agent working one goal tree within one budget. Everything on this page is written for that case, because that is where the field is.

Over time, more goals will be held by groups of agents. The six parts still describe the work, and each part will also need to say which agent holds it. Three new situations follow.

Shared goals

When several agents serve one goal, each needs to see what the others have already done toward it.

Split goals

When one goal is divided among agents, each needs its own share of the budget and its own check for done.

Conflicting goals

When two agents hold goals that pull against each other, the rule for which one wins has to sit above both of them.
